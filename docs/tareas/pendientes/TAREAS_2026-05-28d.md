### CAMBIO 1 — Indicador de cliente seleccionado en POS contado

#### Estado actual

En las 3 vistas de contado, al seleccionar un cliente del dropdown `#clientResults`, la función `selectClient()` hace:
- Rellena `#clientSearch` con el nombre
- Rellena `#clienteIdInput` (hidden) con el id
- Cierra el dropdown
- Opcionalmente muestra `#clientEditPanel` si el cliente es del usuario hoy

**No hay ningún indicador visual de confirmación** — el operador no sabe con certeza qué cliente quedó seleccionado una vez que el dropdown se cierra.

#### Estado en vistas de crédito (referencia)

En las 3 vistas de crédito, al seleccionar un receptor, `#personalInfo` se rellena con:

```html
<div class="alert alert-success py-2">
  <strong>Seleccionado:</strong> NOMBRE — DIP: 12345678
  <span class="badge bg-primary ms-2">UTO</span>  <!-- o bg-warning para externo -->
</div>
```

Este patrón es claro, consistente y ya conocido por el operador.

#### Solución

Agregar un `<div id="clienteSeleccionadoInfo" class="mt-2"></div>` debajo del `#clientResults` en las 3 vistas de contado. En la función `selectClient()`, al seleccionar un cliente, rellenar este div con el mismo patrón `alert-success`:

```html
<div class="alert alert-success py-2 mb-0">
  <i class="ri-user-check-line me-1"></i>
  <strong>Cliente:</strong> NOMBRE — CI: 12345678
</div>
```

Al limpiar el input o cancelar la venta, vaciar el div.

**Casos especiales:**
- "Consumidor Final" (id=0, sin cliente): mostrar badge neutro `alert-secondary` con texto "Consumidor Final — sin CI registrado"
- Al cancelar venta: limpiar `#clienteSeleccionadoInfo`

### CAMBIO 2 — Tamaños de fuente en tarjetas de producto

#### Estado actual (los 3 módulos)

En las tarjetas de producto del grid POS, los tamaños actuales son:

| Elemento | Tamaño actual |
|---|---|
| Nombre del producto | `0.8rem` (ventas/inventarios) / `0.82rem` (agro) |
| Precio (`Bs. X.XX`) | `0.9rem` (ventas/inventarios) / `0.85rem` (agro) |
| Stock (badge) | `0.65rem` (ventas/inventarios) / `0.62rem` (agro) |

El stock es el dato más operativamente crítico en el POS (el operador necesita saber de un vistazo si hay unidades disponibles), pero actualmente es el elemento más pequeño de la tarjeta.

#### Solución

Nuevos tamaños para los 3 módulos (unificados):

| Elemento | Tamaño nuevo | Cambio |
|---|---|---|
| Nombre del producto | `0.82rem` | Sin cambio significativo |
| Precio (`Bs. X.XX`) | `0.88rem` | Ligero aumento |
| Stock (número + unidad) | `1.05rem`, `font-weight: 700` | Aumento notable, negrita |

El stock deja de ser un `badge` pequeño y pasa a ser texto prominente con color del producto:

```html
<!-- Antes -->
<span class="badge" style="background-color: ${colors.border}; font-size: 0.65rem;">
  ${stock} und
</span>

<!-- Después -->
<div style="font-size: 1.05rem; font-weight: 700; color: ${colors.badge}; line-height: 1;">
  ${stock}
  <span style="font-size: 0.72rem; font-weight: 400; color: ${colors.text};">und</span>
</div>
```

| Archivo | Cambio |

### CAMBIO 3 — Imágenes en tarjetas de producto

#### Diagnóstico del estado actual (verificado en BD — 2026-05-28)

**Productos lácteos (`condoriri.productos`):**
- **15 nombres de producto distintos**, todos con `imagen = 'jpg'` (valor placeholder que indica "sin imagen real")
- **0 de 15** tienen imagen subida en `public/uploads/`
- Solo existen 2 archivos en `public/uploads/` con nombres aleatorios (`1769716839_*.png`, `1770382371_*.png`) — probablemente imágenes de prueba sin relación con productos

**Productos agropecuarios (`condoriri.productos_agro`):**
- La tabla **no tiene columna `imagen`** — el campo no existe en el esquema
- Las tarjetas agro usan solo el círculo con iniciales (sin lógica de imagen)

**Mecanismo actual en vistas lácteas:**
Las vistas de contado lácteas tienen un `IMAGE_MAP` hardcodeado que intenta cargar imágenes desde una URL externa (`https://www.uto.edu.bo/wp-content/uploads/2026/03/`). Este mecanismo es frágil (depende de un servidor externo) y actualmente no funciona porque esas URLs no existen.

#### Opciones para proceder

**Opción A — Subir imágenes manualmente por producto (recomendada)**

El operador sube una imagen por cada nombre de producto canónico desde el formulario de edición de producto (`/productos/edit/:id`). El campo `imagen` ya existe en la BD y el formulario ya tiene el input de archivo.

**Problema:** la imagen se guarda por lote (por `id` de producto), no por nombre. Si hay 224 lotes de "QUESO 900 GRAMOS", cada lote tiene su propio campo `imagen`. Subir imagen a todos los lotes es impráctico.

**Solución:** en el POS, al renderizar las tarjetas, buscar la imagen del **lote más reciente con stock** del mismo nombre. Si ese lote tiene imagen real (distinta de `'jpg'`), usarla para todos los lotes del mismo nombre.

Esto requiere que el controller pase `imagen` en los datos de productos al POS. Actualmente ya se pasa el campo `imagen` en el JSON de productos.

**Opción B — Imágenes estáticas por nombre (más simple)**

Subir imágenes a `public/assets/img/productos/` con nombres normalizados (ej. `queso-900g.jpg`, `yogurt-1l.jpg`) y mapearlas en JS por nombre de producto. No requiere cambios en BD ni en el controller.

**Ventaja:** simple, sin dependencias de BD. **Desventaja:** requiere mantener el mapa manualmente cuando se agregan productos nuevos.

**Opción C — Mantener el estado actual con mejora del fallback**

No agregar imágenes reales por ahora. Mejorar el fallback visual: en lugar del círculo con 2 iniciales, mostrar un ícono SVG representativo por categoría (queso, yogurt, leche, etc.) usando iconos de Remix Icon ya disponibles en el proyecto.

**Ventaja:** cero trabajo de assets, mejora visual inmediata. **Desventaja:** no son imágenes reales del producto.

#### Recomendación

**Opción B** para el corto plazo: subir ~7 imágenes a `public/assets/img/productos/` (una por producto canónico con stock) y mapearlas en JS. Es la opción más rápida de implementar y no requiere cambios en BD ni en controllers.

Para el largo plazo, si el cliente quiere imágenes actualizables desde la interfaz, migrar a Opción A con la lógica de "imagen del lote más reciente con stock".

**Para productos agro:** dado que la tabla no tiene columna `imagen`, la Opción B (imágenes estáticas) es la única viable sin migración de BD.

#### Decisión pendiente del cliente

Antes de implementar el Cambio 3, el cliente debe:
1. Elegir entre Opción A, B o C
2. Si elige A o B: proveer las imágenes de los productos (7 imágenes para lácteos, N para agro)

**El Cambio 3 queda en espera hasta recibir confirmación y assets.**
